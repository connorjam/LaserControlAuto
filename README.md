# 激光控制自动化 · LaserControlAuto

在激光驱动调试软件里自动逐点设置参数，等稳定后到测量软件读取数值，全部记录到 CSV。

由 **[MaaFramework](https://github.com/MaaXYZ/MaaFramework)** 驱动

</div>

---

## 它做什么

循环执行下面五步，直到扫完整个区间：

1. 在 A 软件里定位目标参数那一行，清空输入框，填入本轮数值，点旁边的 `Setting`
2. 等待设备稳定（默认 10 秒）
3. 到 B 软件里读取该参数对应的测量值
4. 把「序号 / 设定值 / 测量值 / 时间」追加写入 CSV
5. 换下一个数值

扫描区间、步长或点数、等待时长、结果存放位置都在界面上填，不用改代码。

定位目标控件靠的是实时 OCR，不需要预先量坐标：

- 参数标签（默认 `Temperature`）和同一行的 `Setting` 按钮通过「最近邻配对」锁定，
  界面上有同名文字也不会认错行
- 输入框位置取「标签右边界」到「按钮左边界」之间那块文字，没有文字就取中点
- B 软件的数值先找「标签右边同一行」，再找「标签正下方」

所以换电脑、改窗口大小、改缩放比例都不影响。

## 快速开始

### 环境要求

- Windows 10/11 64 位
- [VC++ 运行库](https://aka.ms/vs/17/release/vc_redist.x64.exe)（缺了会提示「应用程序无法正常启动」）
- 如果启动时提示缺少 .NET，装一下 [.NET Desktop Runtime](https://dotnet.microsoft.com/download/dotnet)
- A 软件和 B 软件都打开，停在含目标参数的那一页

发布包里自带便携版 Python，不需要另外安装。

### 操作步骤

1. 解压发布包，双击 `MFAAvalonia.exe`
2. 控制器选「桌面端」，资源选「默认」
3. 在「扫描设置」里填好起始值、结束值、步长或点数等参数
4. 想在跑完后收到邮件，先在「邮件设置」里填好收件人/发件账号；不确定配没配对，先单独执行一次「邮件测试」任务
5. 勾选「激光参数扫描」任务，点开始
6. 扫描结束后会自动弹出 output 文件夹，到里面取本次的 CSV

任务运行期间不要手动操作鼠标键盘，程序要自己控制 A 软件。中途想停就按界面上的停止按钮。

任务列表里有四个任务，各自独立：

| 任务 | 做什么 |
| --- | --- |
| 激光参数扫描 | 主流程：逐点设参数、读数、写 CSV |
| 邮件通知 | 给最近一次扫描的结果发一封完成通知 |
| 邮件测试 | 立刻发一封测试信，验证邮件配置 |
| 打开输出文件夹 | 只弹出 output 目录，不做别的 |

### 结果放在哪

所有结果都在**软件所在目录**的 `output/` 里，每次扫描占一个子文件夹：

```tree
MFAAvalonia.exe
output/
├── 20261016_110530_output/                  ← 默认按系统时间命名
│   └── 20261016_110530_20_30_11.csv         ← 时间_起始值_终止值_总点数
└── 20261016_143012_升温测试/                 ← 也可以自己命名
    └── 升温测试结果.csv
```

默认文件名把这次扫的参数写进去，翻 output 目录时不用逐个打开就能认出是哪个扫描：

| 扫描设置 | 默认文件名 |
| --- | --- |
| 20 → 30，步长 1（11 组） | `20261016_110530_20_30_11.csv` |
| 20.5 → 21，2 组 | `20261016_110530_20.5_21_2.csv` |
| -10 → 0，3 组 | `20261016_110530_-10_0_3.csv` |

名字里的总点数是**实际跑了几组**，不是界面上填的那个数，这样文件名和 CSV 行数始终一致。

「结果文件夹名」和「结果文件名」留空就用上面的默认值，也可以自己起名。两者都支持时间占位符，可以和中文混写：

| 写法 | 展开为 |
| --- | --- |
| `%Y%m%d` | `20261016` |
| `{date}` / `{time}` / `{datetime}` | `20261016` / `110530` / `20261016_110530` |
| `升温_%Y%m%d` | `升温_20261016` |

名称里 Windows 不允许的字符（`\ / : * ? " < > |`）会自动换成下划线。

### 打开 output 文件夹

任务列表里有个「打开输出文件夹」任务，勾选后点开始就会弹出 output 目录：

- 扫描跑过之后，打开的是上次实际使用的目录（改过「输出总目录」也认得）
- 还没跑过扫描也能用，会打开默认的 output（不存在就现建一个）

它需要控制器连接成功，这是通用 UI 的前提，但不要求 A/B 软件开着。

> Project Interface V2 的配置项只有输入框、下拉框、勾选框、开关和快捷键五种，
> 没有按钮控件，所以这里用一个「点一下就弹文件夹」的任务来充当按钮。

## 扫描设置说明

### 按步长还是按点数

由「扫描点数」这一项决定，两种模式二选一：

| 扫描点数 | 模式 | 例子（起始 20、结束 30） |
| --- | --- | --- |
| `0`（默认）或留空 | 按步长，点数由区间算出来 | 步长 1 → 11 个点；步长 0.5 → 21 个点 |
| `>0` | 按点数，步长自动反算，此时忽略「步长」 | 填 11 → 每步 1；填 6 → 每步 2；填 1 → 只扫起始值 |

按点数时，步长按 `(结束值 - 起始值) ÷ (点数 - 1)` 计算，最后一个点落在结束值上：

```text
起始 20、结束 30、点数 6  →  20, 22, 24, 26, 28, 30
起始 20、结束 30、点数 4  →  20, 23.333333, 26.666667, 30
```

第二种情况除不尽，A 软件的输入框里会出现 `23.333333` 这样的长小数。如果希望每个点都是整数，把区间除以 `点数 - 1` 凑成整数即可。

运行日志里会写明这次用的是哪种模式：

```text
[laser_sweep] 参数序列共 11 组：20 → 30（按步长（1））
[laser_sweep] 参数序列共 6 组：20 → 30（按点数（6 个点，反算步长 2））
```

### 每轮等待秒数

在 A 软件设好参数后等多久再去 B 软件读数。按设备实际稳定时间来填，这一项每减 1 秒，整轮就快 1 秒。

### 读数多点采样（每个点读一秒，取平均）

B 软件的读数本身在抖：同一个参数点上连着读几次，数值能差 0.05 上下，而相邻两组之间的差异也只有这个量级。原来每个参数点只读**一次**，等于随手抓了其中一个瞬间，曲线上的起伏有一半来自读数噪声，而不是设定参数真的改变了被测对象。

现在每个参数点的读法是：

```text
① 定位   整屏 OCR 找到「标签」和它旁边的「数值框」（约 5.5 秒，只做一次）
② 采样   在 1 秒的时间窗里反复读那个数值框，读几次算几次
③ 聚合   剔掉明显误读，剩下的取平均数 → 写进 CSV
```

第 ② 步「一秒读几次」**不写死**，由这台机器 OCR 的实际速度决定：

| 单次读数耗时 | 一秒大约读几次 |
| --- | --- |
| 40 ms | 20 多次（上限 60） |
| 250 ms | 4 次左右 |
| 超过 1 秒（老路径，整屏 OCR） | 1 次，与旧版一致 |

所以同一份代码在工控机和开发机上都能跑：快机器多读几次、平均得更狠，慢机器少读几次，但绝不会为了凑次数把一轮拖长。实际读了多少次会打在日志里：

```text
[laser_sweep] 读数采样：开，每个点读 1 秒，次数由 OCR 速度决定（上限 60 次/点），取平均值写入 CSV
[laser_sweep]   📌 数值框已记住 [200, 300, 130, 24]（锚点旁边那一小块），本轮之后每秒只认它
[laser_sweep]   B 软件 1 秒采样：23 次（0.98 秒，约 43 毫秒/次 ≈ 23.5 次/秒），范围 -79.74 ~ -79.68，平均 = -79.71
```

**平均之前为什么要先剔误读。** 平均值的软肋是它会被离群值拉歪，而且拉歪之后看起来仍然平滑。这一秒里要是混进一个 `-797.20`（小数点右移一位，是这套 B 软件真实出现过的误读形态），23 次采样里只要有 1 次，平均值就从 `-79.7` 变成 `-110.9`，CSV 里就多一个彻底报废的点。所以先用中位数圈出一条「正常带」（±max(绝对 3.0, |中位数|×1%)），带外的判为误读、不参与平均。正常刷新抖动 ±0.05 远远在带内，全都会被平均掉。

顺带把整轮扫描变快了：数值框只需定位一次，之后每秒只认那一小块，

| 环节 | 优化前 | 现在 |
| --- | --- | --- |
| 每轮读 B 软件 | 5.54 秒（每次都整屏 OCR） | 第一轮 6.5 秒（定位 5.5 + 采样 1），之后约 1.1~1.3 秒 |
| 一次重测 | 约 9 秒 | 约 4 秒（同样不用重新整屏定位） |

### 读数环节的速度优化（2026-10-27）

每秒要采十几次样之后，那些原本"可以忽略"的每帧固定开销开始有分量了。下面每一项都是实测出来的（1440x829，即 B 软件客户区），不是估的：

| 项 | 优化前 | 现在 | 怎么测的 |
| --- | --- | --- | --- |
| 位深 | 32bpp 取回再切掉 alpha（多搬 25% 无用字节） | 24bpp，GDI 直接给 BGR | 实测 GetDIBits 0.34ms → 0.25ms |
| 换通道 | `ascontiguousarray(bgra[:,:,:3])` 拷 3.6MB | 24bpp 时 `reshape` 成视图，零拷贝 | 实测 3.10ms → 0.00ms |
| 缓冲区 | 每帧 `create_string_buffer(4.6MB)` | 复用，只增不减 | 实测 1.02ms → 0.00ms |
| 绑定 | 每帧 `WinDLL×2` + 重设 argtypes | 模块级一次性 | 实测 0.04ms → 0.00ms |
| **渲染范围** | 每帧重画整个 1440x829 | **只渲染数值框那一块**（约 146x40） | 实测 895μs → 7.9μs |

合计效果：每帧从 **约 3.5 ms 降到约 0.008 ms**（搬运量降到 0.49%）。同样 1 秒的采样窗，能多读很多次，平均值的代表性也更好。

「只渲染数值框」是怎么做到的：位图只建那块区域那么大，再用 `SetViewportOrgEx` 把绘制原点平移到数值框左上角、`IntersectClipRect` 裁掉区域外的绘制 —— 窗口仍按自己的客户区坐标画，正好落进那块小位图。

> ⚠️ 这条快路径有个前提：窗口要响应裁剪区和视口平移。绝大多数 GDI/WinForms/Qt 窗口都响应；但 DirectComposition 或部分 WPF/UWP 宿主可能无视它们，只返回一块纯色。代码里对此有兜底：检测到整帧只有一种颜色，就自动退回"整窗渲染后裁剪"，并打一行日志。**读数正确性不受影响，只是那台机器上每帧稍慢。**

日志里能看到快路径有没有生效：

```text
[laser_sweep]   B 软件 1 秒采样：23 次（0.98 秒，约 43 毫秒/次 ≈ 23.5 次/秒），范围 -79.74 ~ -79.68，平均 = -79.71；每帧只渲染 146x40 像素
```

看到「每帧只渲染 NxM 像素」且数字远小于窗口客户区，就说明走的是快路径。若显示整窗，通常是 `window_regex` 没配对（那就退回了主控制器截图，没法只截一块）。

界面上这两项可以调：

| 项 | 默认 | 作用 |
| --- | --- | --- |
| 读数采样 | 开 | 关掉就退回旧行为：每个点只读一次 |
| 采样时长 | `1` | 采样时间窗（秒）。填 0 = 只读一次 |

采样时长不建议拉长：仪表一般 100~500 毫秒刷一帧，1 秒已经能覆盖三四帧；再长就会把设备真实的爬升也抹平，而且整轮扫描会明显变慢。

### 读数异常与自动重测

OCR 偶尔会认错一位数字，设备抖动或通信偶发失败也会让单个点跳得离谱。短扫描时人一眼能看出来，跑通宵就没人盯着了，最后拿到一份看不出问题的 CSV。读数校验是给读数加一道门槛：每读到**一个值**（也就是上一节那 1 秒采样的平均数）先和上一次读数比，偏得太多就不急着记录，等一会儿重读同一个点；连续几次都读不回来，就把这个点记成空值、发一封告警，然后按你的设置决定继续扫还是停下来。

#### 真实跳变不会被误杀（2026-10-27 新增）

阈值只能回答「和上一个点差多少」，回答不了「这个新值是真的还是读错了」——这两件事一开始被混为一谈了。翻一次真实运行日志（201 组）就能看到代价：第 176/177 两组被判废，可它们 4~5 次重测彼此只差 0.10~0.23，而下一组立刻回到基准附近。那是设备真实的跳变，两个点白丢了。

所以判据里多了一条：**连续重测的读数如果彼此高度一致，就判为「稳定但待核验的跳变」，接受它并记录，同时打上标记**。逻辑很朴素——随机噪声不会连着 5 次落在同一处。

这条判据的**效力边界必须说清**：同一 OCR、同一位置连读 5 次，不是 5 份独立证据。它只能证明读数**可重复**，不能证明**真实**。如果 OCR 把同一个错值稳定地读错（小数点稳定错位成 `-797.2`），它同样会"彼此一致"从而被接受。所以这类点不会被静默吞掉，而是三处留痕：

| 位置 | 留痕形式 |
| --- | --- |
| CSV | 备注列写 `跳变(自 -14.68)` |
| 完成通知邮件 | 单独一节「需复核的跳变」，列出参数点与跳变前后的值 |
| 日志 | 打印该点被接受的完整判断过程，并提示"只证明可重复，不证明真实" |

「重测内部一致性」的容差是**独立参数**（默认绝对 0.3 / 相对 0.5%），与跨参数点的容差（3.0 / 1%）分开。原因：跨点判据要宽松（不误杀真实波动），而"这几次读数像不像同一个值"要严格——实测真实跳变的内部跨度只有 0.10~0.23，用 3.0 当门槛会把跨度 1.5 的抖动也误认成稳定。

| 形态 | 5 次重测 | 跨度 | 结果 |
| --- | --- | --- | --- |
| 真实跳变 | -18.00 / -18.13 / -18.21 / -18.23 / -18.14 | 0.23 | 接受，记为正常点 |
| OCR 误读 | -95 / -797.2 / -250 / -400 / -320 | 700+ | 判废，发告警 |
| 通信抖动 | -95 / -98 / -92 / -96 / -93 | 6 | 判废，发告警 |

「彼此一致」的判定口径和采样聚合相同：`跨度 ≤ max(绝对阈值, |中位数|×相对阈值%)`。

两个必须说清的边界：

- **稳定不等于真实。** 如果 OCR 把同一个错值连着读 5 次（小数点稳定错位成 `-797.2`，或界面卡死一直显示同一个数），它也会"彼此一致"从而被接受。因此这类点会记进 `jumps`，收尾摘要里列出来「第 N 组接受了跳变：-14.68 → -18.14」，而不是静默改掉。选择"记录 + 留痕"而不是"丢弃"，是因为真实跳变被丢掉会让整条曲线少一个点，比多一个可疑点更难发现。
- **判据只看最近 `retry_max` 个读数。** 更早的异常值已经各自重测过了，把它们的残值混进"稳不稳"的判断里，会让早先的噪声污染当前结论。


| 项 | 默认 | 作用 |
| --- | --- | --- |
| 读数校验 | 开 | 关掉就退回旧行为：读到什么记什么，不做任何比较 |
| 绝对偏差阈值 | `3.0` | 允许的差值上限，管数值较小时的抖动 |
| 相对偏差阈值(%) | `1` | 允许的偏差百分比，管数值本身较大时同比例的抖动 |
| 重测等待秒数 | `3` | 判为异常后等多久再读一次同一个点 |
| 连续异常次数 | `5` | 连续这么多次都不正常就发告警，中间恢复一次就清零重数 |
| 异常后继续测试 | 开 | 发完告警后继续扫下一个点；关掉则终止整个扫描 |

判据是「两条里任意一条成立就算正常」：

```text
正常： |当前值 - 基准| ≤ 绝对偏差阈值
  或者 |当前值 - 基准| ÷ |基准| ≤ 相对偏差阈值(%)
异常： 两条都不成立 → 等「重测等待秒数」后重读同一个点
```

之所以留两条，是因为单一判据在不同量级上会一边过松一边过紧：数值很大时 1.0 的绝对偏差几乎没有约束力，数值很小时百分比又会宽得离谱。两条并存，谁更合适就看谁。对负数也一样，相对判据除的是绝对值，不看正负号。第一个点没有可比的对象，直接记录，并作为接下来的基准。

默认值不是拍脑袋定的，是按实测数据倒推的。一次 20 → 30 的 11 组扫描，功率从 -79.72 只漂到 -80.11，**整段才 0.4**（组间约 0.04）。于是：

- 绝对阈值 1.0 是真实组间波动的 25 倍——正常跑不会误伤
- 相对阈值如果按常理填 10，套在 -79.72 上是 ±7.97，等于给了上百倍于真实波动的余量；判据又取更宽松者，于是相对项永远胜出、绝对项一次都不生效，保护层对这套数据等于没开
- 所以相对阈值默认压到 **1%**（-79.72 上 = ±0.8），让起约束的重新变回绝对阈值

绝对阈值默认 **3.0**（2026-10-27 从 1.0 放宽）。这个数字的定位很明确：它挡的是「离谱」，不是「抖动」——正常波动约 0.04，3.0 是它的 75 倍，正常跑绝不触发；而认错一位数字动辄偏 5 以上，照样抓得住。

举个具体的账。基准读数 -79.72、绝对偏差阈值 3.0、相对偏差阈值 1% 时：

- 绝对判据给的范围是 [-82.72, -76.72]（±3.0）
- 相对判据给的范围是 [-80.52, -78.92]（`1% × 79.72 ≈ 0.8`）
- 两条取并集，实际生效的是更宽的那一个：**[-82.72, -76.72]**

| 读数 | 与基准的差 | 绝对判据 | 相对判据 | 结果 |
| --- | --- | --- | --- | --- |
| -80.5 | 0.78 | 通过（≤ 3.0） | 通过（0.98%） | 正常，直接记录 |
| -82.5 | 2.78 | 通过（≤ 3.0） | 不通过（3.5%） | 正常，直接记录 |
| -83.5 | 3.78 | 不通过 | 不通过（4.7%） | 异常，重测 |
| -85.3 | 5.58 | 不通过 | 不通过（7.0%） | 异常，重测 |

所以正常波动和轻微抖动都照常记进 CSV，而「认错一位数字」「少读一位」这类偏离会在下一轮之前就被拦下重读。

一个容易被忽略的点：**相邻两组之间，设定值本来就在变，读数也会跟着变**。基准是每记下一次正常读数就往前滚一格的，所以缓慢的物理漂移（每步 0.3、0.4）不会被当成异常；只有单步跳变——也就是这几种坏数据的形态——才会触发重测。

| 常见误读形态 | 默认阈值下 |
| --- | --- |
| 小数点右移一位（-79.72 → -797.2） | 抓到 |
| 丢掉负号（-79.72 → 79.72） | 抓到 |
| 少读/多读一位（-79.72 → -7.972） | 抓到 |
| 读成另一个相近的数（-79.72 → -85.3，偏 5.58） | 抓到 |
| 正常波动（-79.72 → -80.11） | 放行 |

反过来说，如果正常数据被判成异常，多半是阈值太紧（把绝对阈值调大），或者上一个点本身就是被误读的值、拿它当了基准，见「遇到问题」。

重测不免费，但正常路径上确实一分钱不花：

```text
正常读数     ：额外耗时约 0.016 毫秒，只多一次减法
一次重测     ：重测等待 3 秒 + 读一次 B 软件 5.5 秒 ≈ 9 秒
连续 5 次异常 ：≈ 45 秒后跳过该组，继续扫下一个点
```

那 0.016 毫秒是怎么量出来的、为什么这么低：判据本身只是一次减法和两次比较；邮件配置**只在真要发信时才去读**，正常读数路径一次磁盘都不碰（读一次配置文件约 0.18 毫秒，虽然小，但它是每一轮都要付的钱）。11 组扫下来，整个校验层累计约 0.18 毫秒，占一轮 18 秒的 0.001%。自检 `check_guard.py` 里有一条断言专门盯着这件事：正常读数 6 轮，读配置的次数必须是 0。

连续异常达到上限之后，程序做四件事：

1. 当前这一组在 CSV 里写一行空值占位，行号仍然和设定参数一一对应
2. 发一封告警邮件：第几组/共几组、总耗时、异常读数列表、最近一次正常读数、允许的偏差、CSV 路径
3. 日志里打印一段摘要
4. **按「异常后继续测试」决定**：默认继续扫下一个点（把这个坏点跳过）；关掉该开关则终止整个扫描

### 异常后继续测试

默认**继续**。理由很实际：告警邮件发出去之后，你未必能立刻过来处理，让它把整轮跑完比停在半路更有用。跳过的那一组会在 CSV 里留一行空值，事后一看行号就知道是第几组废了。

关掉这个开关就退回旧行为：一旦连续异常达到上限，立即终止整个扫描。适合希望「数据一出问题就别再继续产出」的场景。

两种都**会发告警邮件**，区别只在要不要停下。邮件主题也会跟着变——继续模式写「已跳过并继续扫描」，停止模式写「已终止扫描」，免得你半夜看信时误以为扫描停了。

跳过之后，下一个点会重新建立基准（不会拿那个坏值当参照），所以不会连锁误判。

CSV 里多出的那行空值，和「某一轮读数失败」是同一种处理，读法见「结果格式」。

### 邮件通知：三种用途，一套配置

邮件相关的能力拆成三处，**但账号/授权码/收件人只有一份配置**（「邮件设置」），改一处全生效：

| 任务 / 开关 | 什么时候发 | 在哪开 |
| --- | --- | --- |
| **邮件通知**（独立任务） | 扫描跑完后发一封汇总信：扫了几组、成功几组、哪些行是空值、耗时、文件路径 | 任务列表里单独勾选执行；开关是「邮件设置 → 扫描结束后发送完成通知」 |
| **邮件测试**（独立任务） | 立刻发一封测试信，验证配置对不对 | 任务列表里单独勾选执行 |
| 读数异常告警 | 连续多次读数异常、扫描被终止时发 | 扫描任务的「读数异常时发送邮件」勾选框 |

拆开的好处有两个。一是**扫描任务的参数从 19 项降到 10 项**，被 `pipeline_override` 整体替换时漏字段的风险小得多（漏一个就等于把你填的配置抹成默认值，这个坑本项目踩过）。二是邮件配错了不会让「读数检测」看起来也出了问题——两者彻底解耦。

「邮件测试」值得单独说：邮件配错平时完全看不出来，只有等到「连续 5 次读数异常」那一刻才暴露，而那正是最不该发现「原来邮件一直发不出去」的时候。所以给了一个随时可点、立刻给结论的自检入口。

### 通知方式

| 通知方式 | 行为 | 什么时候用 |
| --- | --- | --- |
| `auto` | 收件邮箱、SMTP 账号、SMTP 密码/授权码都齐了才发，没配就只写日志 | 不想被配错打扰时 |
| `email`（默认） | 强制发信，缺凭据会失败并把原因写进日志 | 平时用它——配错了会立刻暴露，不会静默退化成"只写日志" |
| `off` | 完全不发，只在日志里留摘要 | 机器不能连外网，或者有人盯着屏幕 |

一次任务最多发 1 封是默认的（「一次任务最多发几封」），只约束**告警**；「邮件通知」和「邮件测试」各算各的，不会被告警限额挤掉。

### 授权码放哪：本地配置文件

授权码**不要**写进 `interface.json` / `my_task.json`：那两个文件是入库的，一提交就等于把邮箱公开了。所以它单独放一个本机文件：

```text
开发时：  assets/config/laser_sweep_mail.json
打包后：  <软件目录>/config/laser_sweep_mail.json
```

`.gitignore` 里的 `config` 一行已经把它挡住了（`git status` 里看不到）。

```jsonc
{
  "notify_mode": "email",
  "smtp_host": "smtp.qq.com",
  "smtp_port": 465,
  "smtp_ssl": true,
  "smtp_user": "你的发件邮箱@qq.com",
  "smtp_password": "授权码",
  "mail_to": "收件邮箱@qq.com",
  "mail_subject_prefix": "[激光扫描]"
}
```

界面参数与它的优先级是：**界面填了 > 本地配置文件 > 内置默认值**。也就是说界面上留着空就行，程序会自动去读这个文件；哪天想换收件人，改界面那一栏即是以界面为准，不会被文件里的旧地址盖掉。换电脑时把这个文件拷过去即可，不必重新申请授权码。

要真的发出信，服务器、端口、账号、密码四项得填对。下面按常见邮箱给一组可直接照抄的配置：

| 邮箱 | SMTP 服务器 | 端口 | 加密 | 授权码在哪拿 |
| --- | --- | --- | --- | --- |
| QQ 邮箱 | `smtp.qq.com` | `465` | SSL | QQ 邮箱 → 设置 → 账户 → 开启 SMTP 服务 → 生成授权码 |
| 163 邮箱 | `smtp.163.com` | `465` | SSL | 163 邮箱 → 设置 → POP3/SMTP/IMAP → 开启服务 → 新增授权码 |
| 企业邮箱 | 找 IT 要 | `465` 或 `587` | SSL / STARTTLS | 由管理员开通 SMTP，给的可能是授权码，也可能是专用密码 |


**「SMTP 密码/授权码」里填的是授权码，不是邮箱登录密码。** 登录密码交出去等于整个邮箱失守，所以各家都另发一个只用于 SMTP 的授权码，可以单独停用而不影响其他设备的登录。界面上这一项是掩码显示的，日志里也只打印「填了什么、几位」，不会把内容写进日志或错误信息。

发出来的邮件大致长这样：

```text
标题：[激光扫描告警] 读数连续 5 次异常，扫描已终止

本次扫描：20 → 30，共 11 组，已完成 7 组
卡住的位置：第 8 组，设定参数 27
总耗时：2 分 41 秒（开始于 2026-10-26 14:30:12）
机器：DESKTOP-7F2K

最近一次正常读数：-79.94（第 7 组，设定参数 26）
异常读数：
  第 8 组 设定 27 → -95.31
  第 8 组 设定 27 → -95.28
  （共 5 条，按时间顺序）

允许的偏差：绝对 1.0，相对 1%
结果文件：D:\LaserControlAuto\output\20261026_143012_output\20261026_143012_20_30_11.csv

请检查 B 软件是否还在出数、A 软件是否卡住。
```

「最近一次正常读数」和「允许的偏差」是特意放进去的：半夜看到告警，得先知道正常数据应该长什么样，才知道这次偏了多少。

公司网络里 465/587 这类出站端口常被防火墙封掉，表现是发信超时。邮件发不出去不影响扫描终止——终止、写 CSV、打印摘要照常完成，只有日志里 `✉️` 那一行会带上失败原因。怀疑是端口被封时，用手机热点试一次就能确定：能发出去就是网络问题，找 IT 放开端口即可。

### 输出设置

| 项 | 作用 | 默认 |
| --- | --- | --- |
| 结果文件夹名 | 本次结果放在 `output/` 下的哪个子文件夹 | 留空 = `系统时间_output` |

## 结果格式

CSV 用 UTF-8 BOM 编码，Excel 双击打开不乱码：

| 序号 | 设定参数 | B软件测量值 | 时间 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | 20 | -79.72 | 2026-09-22 16:51:25 | |
| 2 | 25 | -79.94 | 2026-09-22 16:51:32 | |
| 3 | 30 | -80.11 | 2026-09-22 16:51:58 | |
| 4 | 35 | -18.14 | 2026-09-22 16:52:20 | 跳变(自 -14.68) |

「备注」列留空 = 这一行是常规读数。有内容说明这一行需要人复核：

| 备注 | 含义 |
| --- | --- |
| `跳变(自 -14.68)` | 连续多次重测都偏离上一个可信值（-14.68），但它们彼此高度一致，判为设备真实跳变后接受 |
| `读数失败` / 其他原因 | 这一行是空值占位 |

⚠️ `跳变` 标记的含义要说清：它只证明读数**可重复**，不证明**真实**。同一 OCR、同一位置连读 5 次不是 5 份独立证据——如果 OCR 把同一个错值稳定读错（小数点稳定错位），也会得到这个标记。所以这类点必须人工看一眼，不能当常规数据直接用。

某一轮读数失败时会写一行空值占位，保证行号和参数一一对应，不会错位。连续多次读数异常时，当前这一组也会这样写空值占位（继续扫描模式下跳过该组、停止模式下终止扫描），处理方式相同。

## 速度与调优

在开发机（1331x720 窗口）上实测，一轮大约 18 秒。第一轮会慢一些（约 23 秒），因为它要跑一次 OCR 建立定位缓存。

| 环节 | 优化前 | 现在 |
| --- | --- | --- |
| 全屏 OCR 找 `Temperature` / `Setting` | 4.57 秒 × 2 | 只第一轮一次，之后复用缓存 |
| 等设备稳定 | 10 秒 | 10 秒 |
| 读 B 软件 | 5.54 秒（每次都整屏 OCR） | 第一轮约 6.5 秒（定位 + 1 秒采样），之后约 1.1~1.3 秒；截图链路优化后每帧渲染量降到 0.5% |
| 清空输入框 | 约 4.1 秒（32 次退格） | 约 1.5 秒（12 次） |
| 等画面冻结 | 约 4.3 秒 | 0.2 秒 |
| 点击 / 输入 / 框架调度 | 约 1.1 秒 | 约 1.1 秒 |
| 合计 | 约 34 秒/轮 | 约 18 秒/轮 → 读数改采样后约 14 秒/轮 |

读数采样看着"多读了好几遍"，实际并不更慢：整屏 OCR 那 5.5 秒一輪只付一次，之后每秒只认数值框那一小块。反而是旧版每轮都要整屏 OCR 一次。

读数校验不在这张表里：正常读数不增加任何耗时，只有出现异常才会多出「重测等待 + 重读」的时间，重测一次约 4 秒（旧版约 9 秒 —— 同样因为不必重新整屏定位）。

想再压时间，按收益从大到小：

1. **每轮等待秒数**。设备多久稳定就填多少。
2. **定位缓存**。`my_task.json` 里 `LaserSweepFindTemperature` 和 `LaserSweepClickSetting` 的 `custom_recognition_param` 可调：

   | 参数 | 默认 | 含义 |
   | --- | --- | --- |
   | `use_cache` | `true` | 写 `false` 就退回每次都重新 OCR |
   | `cache_ttl` | `600` | 缓存有效期（秒），`0` 表示不因时间失效 |
   | `relocate_every` | `0` | 每复用几次强制重认一次，长跑可以写 `20` |
   | `hint_roi_pad` | `240` | 缓存失效后用「上次位置外扩」的小区域先试一次 |

   截图尺寸变化（窗口被移动或缩放）时缓存自动作废，不会拿旧坐标去点。

3. **`LaserSweepClearField` 的 `repeat`**。够清掉输入框旧值就行。如果日志里发现数值被拼接（如 `20.525`），说明清得不干净，把它调回 32。

日志里可以确认缓存是否生效：

```text
[laser_sweep]   📌 已缓存 A 软件控件位置：anchor=[497, 293, 95, 16]；target=[726, 292, 61, 20]；input=[592, 292, 134, 20]
[laser_sweep]   ♻️ 复用定位缓存（return_box=input）[592, 292, 134, 20]；已复用 3 次，缓存 12 秒
```

流水线里节点之间没有额外延时。框架默认的 `rate_limit`（1000 毫秒）和 `pre_delay` / `post_delay`（各 200 毫秒）已逐个显式压成 0，调整速度只需要看上面几项。

## 遇到问题

| 现象 | 处理 |
| --- | --- |
| 任务列表是空的，点 + 也没任务 | `interface.json` 没加载成功，日志里会有「文件 interface.json 加载失败」。常见原因是 `welcome` 写成了字符串数组，见[打包文档](docs/zh_cn/develop/packaging.md) |
| 点开始没反应，A 软件没被操作 | 确认 A 软件已打开，窗口标题和配置一致 |
| 提示找不到窗口 | 窗口标题变了，见「适配其他软件」 |
| 数值一直读不到 | B 软件没开，或者标签文字不对 |
| CSV 里测量值全是空的 | 读数失败，看日志里的 OCR 结果 |
| 日志里 `1 秒采样` 只显示 1 次 | 这台机器 OCR 单次就超过采样窗（日志会写「只能读 1 次」）。数据照样正确，只是没做平均；想多读几次可以把「采样时长」调大 |
| 数值和手抄的对不上（略高/略低） | 这是正常的：CSV 里是那一秒的**平均**，人眼看到的是屏幕上某一瞬间的瞬时值 |
| A 软件参数没被改，或点到别处 | 看日志里的 `锚点候选`、`按钮候选`、`点击 (x, y)`，能看出它选了谁、点在哪；选错就用 `near_text` 指定标签 |
| 改了定位缓存之后点偏 | 缓存只在截图尺寸没变时复用。如果怀疑它拿旧坐标硬点，把节点的 `use_cache` 写成 `false` |
| 数值被拼接（如 `20.525`） | 退格次数不够，把 `LaserSweepClearField.repeat` 调回 32 |
| 日志里一条 `[laser_sweep]` 都没有 | 用的是 v1.0.4 之前的老包，换新版 |
| 扫描中途停了，没跑完 | 只在「异常后继续测试」关掉时才会发生：连续读数异常触发了保护。看日志摘要和邮箱，确认是设备真的读数异常，还是阈值定得太紧。想让它继续跑完就把那个开关打开（默认就是开的） |
| 某几行是空的，但扫描跑完了 | 这几组连续多次读数异常，被跳过并记了空值（继续测试模式）。看邮箱里的告警信确认当时读到了什么 |
| 没收到邮件 | 依次确认：「通知方式」是不是 `off`，或者 `auto` 但收件邮箱、SMTP 账号没填；密码那一栏填的是不是授权码而不是登录密码；公司网络有没有封 465/587。日志里 `✉️` 那行会写明失败原因。也可以先单独执行一次「邮件测试」任务 |
| 收到完成通知，但没收过异常告警 | **2026-10-27 已修**。此前扫描任务只挂了「扫描设置」、「邮件设置」没挂上，导致 Guard 拿不到 SMTP 配置，告警一律静默降级为不发；而完成通知由「邮件通知」任务发出（它挂了邮件设置），所以看起来"邮件是通的"。修复后扫描任务也挂「邮件设置」，日志开头会有 `告警邮件：已从「邮件设置」读到 …`。若仍看到 `缺少配置：smtp_host…`，说明用的是旧包 |
| CSV 行数比计划点数多 | **2026-10-27 已修**。此前连续异常判废时，空值行由 Guard 写一次、又跳回 Record 写第二次，201 组会变成 203 行且行号错位。修复后判废直接跳 Advance，空值行只写一次 |
| 相对偏差填 0.5 却不生效 | **2026-10-27 已修**。此前小于 1 的数值会被当作"比例"乘 100，填 0.5 实际变成 50%，保护层形同虚设。现在统一按界面声明的百分数解释：填 0.5 就是 0.5% |
| 填「重测等待 0」还是等 3 秒 | **2026-10-27 已修**。此前只有大于 0 才覆盖节点延时，填 0 时节点仍保留默认 3000 毫秒。现在 0 也会显式写入 |
| 界面改了起始值，扫描还是从 20 开始 | **2026-10-27 已修（严重）**。此前「扫描设置」和「邮件设置」两个 option 都写了 `LaserSweepStart` 的 `pipeline_override`，而 override 对 `custom_action_param` 是**整体替换**：后应用的那份把 `start/end/step/count` 整个顶掉，agent 退回代码默认的 20→30。修复后 `LaserSweepStart` 只由「扫描设置」覆盖（邮件字段也写在那一份里），`check_sample.py` 里有断言盯着"同一节点不许被两处覆盖" |
| 日志显示每秒十几次，但 CSV 像是单点值 | **2026-10-27 已修**。采样快路径里 `region=None` 分支对 `None` 做了 `tuple()` 抛 `TypeError`，异常被采样循环吞成"这次跳过"，于是十几次尝试全部静默失败、只剩定位时那一个样本。修复后 `region=None` 正常取整图；现在只要失败次数 > 0，日志会明确写「这一窗尝试 N 次，成功 M 次、失败 K 次（xx%）；最常见原因：…」 |
| 正常数据也被判成异常了 | 阈值太紧，或者前一个点本身就被误读、拿它当了基准。把绝对偏差阈值调大（默认已放宽到 3.0），或者把相对偏差阈值调大 |
| 提示「应用程序无法正常启动」 | 装 VC++ 运行库 |

日志在通用 UI 的运行日志面板（agent 的打印都以 `[laser_sweep]` 开头），框架层细节在 `debug/maafw.log`。

## 适配其他软件

### 换 B 软件（读数的那个）

编辑 `resource/pipeline/my_task.json`，找到 `LaserSweepReadValueB`，改两处：

```jsonc
// 窗口标题，用 ^...$ 锚定；多套软件可以用 | 写在一起
"window_regex": "^(GaussianBeam|光器件耦合系统.*)$",
// 要读的量的标签，可以写数组，任一命中即可
"anchor_text": ["功率CH1", "Wavelength"],
```

数值靠位置识别，程序按顺序尝试：先找标签右边同一行的数值，再找标签正下方的数值，两条都不成立才退回「离标签最近」并打印警告。

两点注意：

- `anchor_text` 不要写成 `"CH1"` 这种既当标签、自身又含数字的词。宽松正则会先在标签自己身上匹配出 `1`，导致每轮都读到 1。现在有「候选不能和标签重叠」的规则兜着，但标签写得越明确越稳。
- `window_regex` 要加 `^...$`。标题叫 `GaussianBeam` 时，不加锚点会连「GaussianBeam - 文件资源管理器」一起匹配上。

### 换 A 软件（操作的那个）

| 改哪里 | 改成什么 |
| --- | --- |
| `interface.json` → `controller[].win32.window_regex` | A 软件的窗口标题 |
| `my_task.json` → `LaserSweepFindTemperature` 的 `anchor_text` | 参数标签文字 |
| `LaserSweepFindTemperature` 的 `near_text`（可选） | 界面上有多个同名标签时，指定用哪一个 |

不需要量任何坐标或 `roi`。

界面上有多个同名标签时（比如两个 `Temperature`），有两种指定方式：

```jsonc
"anchor_text": "Temperature",
"near_text": ["Module Config", "ModuleConfig"],  // 取离这个词最近的那个
// 或者按顺序数：
// "anchor_index": 1,                            // 从上到下第 2 个（0 是第一个）
```

`near_text` 没命中时日志里会打警告并退回原逻辑。每次运行还会打印 `锚点候选：...` 和 `按 near_text=... 钦定锚点 ...`，对着日志就能确认选对没有。

标签、按钮、数值三者都只接受短文本（由 `anchor_max_chars`、`target_max_chars`、`value_max_chars`、`min_digit_ratio` 控制）。界面上的提示行和日志行动辄几十个字，只要含关键词就可能被误认成标签或数值，所以按长度卡了一刀。日志里的 `锚点候选`、`按钮候选` 会列出过滤后的名单。

## 开发者：打包

完整说明见 [`docs/zh_cn/develop/packaging.md`](./docs/zh_cn/develop/packaging.md)。两条路：

**本地打包**：准备好 `deps/`（MaaFramework）和 `MFA/`（MFAAvalonia），然后

```bash
python tools/prepare_embedded_python.py
python tools/install.py v1.0.17 win x86_64
python tools/pack_zip.py
```

产物在 `dist/LaserControlAuto-win-x86_64-v1.0.17.zip`。

**CI 自动打包**：打一个 tag 推上去，GitHub Actions 会自动打包 Windows x64 版并创建 Release。

```bash
git tag v1.0.17
git push origin v1.0.17
```

### 热修复包

只改了 agent、流水线或界面配置时，不必重发全部内容，可以只打一个几十 KB 的覆盖包：

```bash
python tools/pack_hotfix.py v1.0.17
```

产物 `dist/LaserControlAuto-v1.0.17-hotfix-files.zip` 里包含三个文件：

| 文件 | 负责 |
| --- | --- |
| `agent/laser_sweep.py` | 逻辑：定位、读数、扫参序列 |
| `resource/pipeline/my_task.json` | 流程：节点、延时、默认参数 |
| `interface.json` | 界面：输入项和 `pipeline_override` |

解压后覆盖到 `MFAAvalonia.exe` 所在的那一层。脚本会打印每个文件的字节数和 md5，使用者对着运行日志里 `[laser_sweep] agent 文件：…` 那行就能确认替换成功。

`interface.json` 不能漏。界面上的输入项全部定义在它的 `option.*.inputs` 里，agent 和流水线只是接收方。只覆盖前两个文件的话，新增的输入项在别的电脑上不会出现，而本机因为 `install/` 已经被 `install.py` 重写过，看着却是正常的，很容易误判成热修复没生效。**动了界面输入项或 `pipeline_override`，就必须连 `interface.json` 一起发**，`tools/pack_hotfix.py` 的默认文件列表已包含它。

打包源是 `install/` 里的副本。`install/` 由 `tools/install.py` 从 `agent/` 和 `assets/resource/` 拷过来，脚本会先比对两边是否一致，不一致就停下并提示（用 `--sync` 就地同步，`--force` 按现状强打）。`interface.json` 不参与比对，因为它本来就该和 `assets/interface.json` 不同（版本号、agent 路径、`welcome` 都被 `install.py` 改写过）。

### 自检脚本

改完定位逻辑或输出逻辑，可以不连软件先跑一遍自检：

```bash
python tools/check_pickers.py   # 定位、读数、扫参序列、点数模式
python tools/check_output.py    # 输出目录、文件名、时间占位符、开关
python tools/check_guard.py     # 读数校验、重测跳转、连续异常终止、告警邮件
python tools/check_sample.py    # 1 秒多点采样：次数由时间决定、取平均、剔误读、配置一致性
```

四个脚本都用桩模块顶掉 `maa`，直接调纯函数，几秒钟跑完。

`check_guard.py` 里有几条是拿真实跑数当样例的：它断言默认阈值下「正常组间漂移放行、认错一位数字被抓」，也断言第 5 次异常之后跳的是终止节点、邮件正文里确实写了总耗时和期望值范围。改阈值相关代码后跑一遍，能挡住「把保护层改瞎了却没人发现」这类回归。它不会真的发信 —— SMTP 是换成假对象测的，凭据也是假的。

`check_sample.py` 盯的是采样这一层：它把「OCR 速度」做成可控的假函数，断言**快的机器读得多、慢的机器读得少**（同一份代码，一秒内采样次数不同），并断言一个 `-797.20` 这样的误读不会把平均值拉成 `-144`。最后还有一条配置一致性断言：`interface.json` 的覆盖块与 `my_task.json` 的默认值字段集合必须完全一致 —— 因为 `pipeline_override` 对对象是整体替换，少写一个字段就等于把它抹掉。
